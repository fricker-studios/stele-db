# Codebase audit — July 2026 (v0.3.0)

A full sweep of the workspace for completeness, correctness, security, performance,
and documentation. This file is the **backlog of what was found and deliberately
not fixed in the audit pass** — each entry is meant to become a ticket. What *was*
fixed in the same pass is listed at the bottom for context.

Severity is about impact if reached, not likelihood:

| | |
|---|---|
| **P0** | Data loss, isolation violation, auth bypass, or remote process kill |
| **P1** | Correctness edge, durability window, or resource exhaustion |
| **P2** | Performance cliff, hardening gap, scaling ceiling |
| **P3** | Docs, naming, ergonomics |

Two facts raise the stakes on everything below and are worth stating once:

* `[profile.release] panic = "abort"` (`Cargo.toml`) — **any** reachable panic is a
  full-process kill, not a failed query. "Defensively unreachable" is a weaker
  position here than it would be under unwinding.
* `stele_sql::parse` runs inline on a tokio worker with no `spawn_blocking`
  (`stele-pgwire/src/lib.rs`), so a slow parse stalls a runtime worker.

## 1. Security posture

### 1.1 — P0 — There is no authorization model

`apply_user_ddl` (`stele-engine/src/lib.rs`) takes no principal and performs no
privilege check, and `execute_at` routes `StatementBody::Admin` unconditionally.
So any authenticated session can run `ALTER USER admin PASSWORD …`, `CREATE USER`,
`DROP USER`, or any admin verb. SCRAM (STL-252/297/298) authenticates an identity
that nothing then consumes for access control, which makes one account compromise
a full compromise and reduces the whole auth investment to provenance stamping.

Needs: a role/privilege concept, a superuser distinction, and a check at the DDL
and admin-verb entry points. This is the single largest gap between the security
posture `docs/10` describes and what the code enforces.

### 1.2 — P0 — `--dev` defaults to on and cannot be turned off

`crates/stele-server/src/main.rs` declares `#[arg(long, default_value_t = true)] dev: bool`.
clap maps `bool` to `SetTrue`, so there is no `--no-dev`: a bare `stele-server`
runs `Config::dev()` — `AuthMode::Trust`, no TLS, bound `0.0.0.0:5454` — and
`plaintext_posture`/`auth_posture` both short-circuit on `cfg.dev`, so **not even a
warning** is emitted. The only escape is `--config`.

The test `dev_mode_is_friction_free_even_off_loopback` pins this as intended, so it
is a deliberate product decision rather than an oversight — but the decision means
the default invocation of the daemon is an unauthenticated database on all
interfaces, silently. Recommended: default `dev` to `false` and have the
documented five-minute path pass `--dev` explicitly (the Docker image, compose
file, and CI smoke test already do), or bind dev mode to loopback.

### 1.3 — P0 — mTLS + `tls mode = "optional"` is an authentication bypass

`auth_posture` (`stele-server/src/lib.rs`) suppresses the "UNAUTHENTICATED" boot
warning whenever `client_ca.is_some()`, on the theory that the client certificate
is the authentication story. That holds only under `TlsMode::Required`. Under
`"optional"` a client may send a plaintext `StartupMessage` — no handshake, so no
client certificate — and `run_session` falls to the trust arm and takes the
startup `user` verbatim. Configure `[tls] mode="optional", client_ca=…` with no
`[auth]` and any reachable peer is any principal, with no warning.

Fix: require `client_ca.is_some() && mode == Required` before suppressing, and
refuse a plaintext startup whenever `client_ca` is configured.

### 1.4 — P1 — `BACKUP TO '<path>'` is an unauthenticated arbitrary-path write

`apply_admin` passes the SQL literal straight to `LocalDisk::open`, which is
`create_dir_all`. Any session can create directory trees anywhere the process can
write and copy the entire database — every segment, WAL, `stele.catalog` (which
holds SCRAM verifiers) and `stele.commits` — to a location of its choosing. Note
the contrast one layer down: `LocalDisk::path` runs `validate_name` to keep *file*
names inside the root; the backup *root* is unvalidated caller input.

Fix: confine targets to a configured backup root (join + canonicalize + verify
containment), and gate behind the privilege model from 1.1.

### 1.5 — P1 — Plaintext passwords reach the log at INFO

`stele-pgwire/src/lib.rs` logs the full statement text on the DDL failure paths
(`info!(query = %sql, …)`). `CREATE USER` / `ALTER USER … PASSWORD` is DDL, so a
*failed* one — duplicate user, unknown user, a typo — writes the cleartext
password into the log stream. The engine never persists the password and
`ScramVerifier`'s `Debug` redacts key material; the wire layer undoes both.

Fix: omit `query` on those paths, or scrub `PASSWORD '…'` before logging.

### 1.6 — P1 — No connection limit, no authentication timeout

The pg-wire accept loop spawns unconditionally per socket, and there is no timeout
on the startup/auth phase or the TLS handshake (the *admin* listeners do have
`HANDSHAKE_TIMEOUT`; pg-wire was missed). Combined with 1.7, a few kilobytes of
traffic parks unbounded server memory. Postgres bounds this with `max_connections`
+ `authentication_timeout`; there is no equivalent.

### 1.7 — P1 — Pre-auth allocation is committed before payload arrives

The message reader honors the 16 MiB cap but does
`BytesMut::with_capacity(payload_len)` + `resize` **before** reading any payload
byte, and this is reachable pre-auth via `read_sasl_message`. 2,000 sockets each
declaring 16 MiB and then going quiet is ~10 KB of attacker traffic for ~32 GiB
resident.

### 1.8 — P1 — COPY lexing amplifies its input ~120×

The 1 GiB `MAX_COPY_BUFFER_SIZE` bounds the *input*; `copy::lex` then expands it
into per-row `Vec`s and per-field `Option<String>`s. 1 GiB of newlines yields
~10⁹ single-field rows ≈ 120 GiB of allocation. Cap rows/fields during lexing, or
land the STL-240 streaming path.

### 1.9 — P2 — Unbounded per-connection state

Three caches with no ceiling: prepared statements and portals (`HashMap`s, never
evicted — a client can `Parse`/`Bind` distinct names forever, each retaining an
AST or a materialized result set), and `SessionTransaction::writes` (notably
`copy_stage` has no chunking, unlike the auto-commit path's `BULK_COPY_CHUNK_ROWS`).
An idle `BEGIN` additionally pins the write-index prune floor forever — there is no
idle-in-transaction or statement timeout anywhere.

### 1.10 — P2 — Unauthenticated ops listener on `0.0.0.0:9090`

`/healthz`, `/readyz`, `/metrics` have no credential check (only `/v1alpha1` goes
through `AdminAuth`), the listener has unbounded connection concurrency, and its
timeout is per-read rather than per-request — an unauthenticated slowloris. The
gRPC path got the backlog semaphore right; the ops listener, which is the one bound
wide by default, did not.

### 1.11 — P2 — File permissions are never checked

Neither `stele.toml` (which carries `[admin] tokens`) nor the TLS private key has
its mode checked at load. Postgres refuses to start on a group/world-readable
server key; Stele serves happily — and CI depends on the laxity
(`chmod 644 server.key` in `ci.yml`). The project already has the right pattern in
`stele-cli/src/pgpass.rs`, which refuses `mode & 0o077 != 0`.

### 1.12 — P2 — CLI accepts any server certificate under `sslmode=require`

`stele-cli/src/client.rs` installs `AcceptAnyServerCert` for both `Prefer` and
`Require`. Combined with a silent downgrade out of channel binding when the leaf's
signature algorithm isn't recognized (Ed25519, RSASSA-PSS — all attacker-choosable)
and an unconditional `AUTH_OK => {}` arm, an active MITM defeats `--tls require`.
The module doc claims the PLUS path defeats a terminating MITM, which is true only
when the MITM cooperates.

### 1.13 — P2 — Terminal-escape injection in the shell

`display_cell` correctly escapes control characters in *row cells*, but column
names (`render.rs`) and server error `message`/`hint` text (`shell.rs`) are painted
raw. A malicious server can repaint the terminal, spoof a "connection secured" line,
or (where OSC 52 is enabled) write the clipboard. `json_lines` escaping is also
narrower than `display_cell`'s — it misses DEL and the C1 block including CSI.

### 1.14 — P2 — Container runs as root; base images unpinned

`docker/Dockerfile` uses `gcr.io/distroless/cc-debian12` (the plain tag, UID 0)
with no `USER`, and both `FROM`s are floating tags while every `uses:` in CI is
40-char-SHA-pinned — the build inputs that actually ship are the least pinned thing
in the pipeline. `EXPOSE` also omits 9090 and 5455. Separately, `release.yml` pushes
`:latest` on every tag including prereleases.

## 2. Durability & recovery

### 2.1 — P0 — A torn WAL tail is tolerated once, then never repaired

`Wal::open` sets `staged_end`/`durable_end` to `current.len()` without validating
contents, and `DiskFile` has no truncate. So the stray bytes of a crash-torn frame
stay at offset *P* forever and post-recovery records land after them, while
`Replay::read_record` stops at the first bad frame permanently. Second recovery
then either **silently drops every commit written after the first recovery** (no
checkpoint since) or **fails permanently** (`replay.position() < fence`). Only
`Engine::flush` advances `replay_floor` past *P*, and the session engine flushes
only on explicit `FLUSH`/`BACKUP`/bulk-`COPY`.

Fix: repair rather than tolerate — add a truncate to the local backend and cut the
head segment back at recovery, or force a rotation after a tolerated tear and
persist *P* so a later replay treats corruption at exactly that offset as
end-of-segment.

Every crash test in the tree crashes exactly *once*; this is the class of bug that
hides behind that.

### 2.2 — P0 — The torn-tail gate keys off the checkpoint fence, not the fsync point

With no manifest record, `fence = LogOffset::ZERO`, and the tolerate test
(`position() >= fence`) is then true everywhere — so corruption at *any* offset is
treated as a benign tail. 10,000 acknowledged commits with no `CHECKPOINT` ever
issued plus one bit-rot in record 3 recovers `Ok` having dropped 9,997 of them.
This directly contradicts `docs/02-architecture.md` §3.7 ("a *complete* frame whose
CRC fails is corruption of acknowledged history and **fails closed**"), which holds
only below the last checkpoint.

### 2.3 — P0/P1 — The catalog log has no poison and no write-position validation

`catalog_log::append` does `file.append(&frame)?; file.sync()?;` with neither
failure fenced, and there is no `catalog_poisoned` flag. Two outcomes:

* **Torn append** — debris stays at the tail; the *next* successful DDL appends past
  it, which makes the partial frame parse as *complete* (the file is now longer, so
  the tear check no longer fires) and its CRC fail → **the database is permanently
  unbootable**.
* **Append succeeds, fsync fails** — the DDL is reported failed but replays on the
  next boot; once a later DDL chains from the stale head, replay reports
  `"hash-chain broken … (tampered DDL history)"` and the database is unbootable and
  *misdiagnosed*.

`EngineError::CatalogLog`'s rustdoc asserts "the DDL is refused — nothing was
acknowledged", which is false in both cases. The existing test injects a *clean*
`FaultOp::Append` (nothing lands) and never `FaultOp::Sync`, so both windows are
untested. This is the same doctrine the per-table WAL (STL-217) and commit log
(STL-314) already apply; the catalog log is the outlier.

### 2.4 — P1 — A corrupt length silently truncates the catalog log

In `catalog_log::replay` the torn-tail test runs *before* the `MAX_RECORD_PAYLOAD`
check, so a bit-flip inflating a mid-log record's length past EOF is
indistinguishable from a tear: replay breaks and boot **succeeds** with a silently
truncated catalog — tables vanish, a `DropUser` un-drops and restores a deleted
account's credentials, and every subsequent DDL is appended past the garbage. Move
the cap above the tear check, or add a CRC over the 8-byte header so framing is
self-validating.

### 2.5 — P1 — A failed multi-table commit leaves committed legs readable

Once one leg fails, `finish_group_commit` aborts the *remaining* tables; legs that
already succeeded are neither undone nor discarded. `COMMIT` returns an error, the
client sees `ERROR`, and other connections can read the failed transaction's rows
until a restart makes them vanish. Documented as an STL-216 follow-up, but the doc
frames it as an in-memory nicety when it is a client-visible atomicity break plus a
live/recovered divergence. Secondary: those keys stay in `write_index`, causing
spurious `40001` for others.

### 2.6 — P1 — An all-zero WAL frame is a valid zero-length record

`crc32c(b"") == 0` and the frame header is `len:u32 | crc:u32`, so eight zero bytes
parse and verify as a well-formed empty record. Replay walks a zero-filled hole 8
bytes at a time reporting success. Filesystems that expose zeroed blocks after a
crash (ext4 delayed allocation, some thin-provisioned devices) make this reachable.
A nonzero record magic or a `len == 0` rejection closes it.

### 2.7 — P1 — A WAL segment hole is skipped rather than refused

`Replay::read_next` advances to the next *existing* segment index, not `seg + 1`,
so a missing `wal-…0003.log` is hopped over and replay keeps applying — recovery
"succeeds" with closes referencing versions that were never inserted. If the
checkpoint's floor names a segment that no longer exists, `binary_search` misses and
replay yields **zero** records, also reported as success.

### 2.8 — P1 — `Engine::flush` has no guard against an open group

Group-mode writes apply to the delta *before* their WAL record exists, and `flush`
snapshots `delta.staged_versions()` with no check that a group is open — sealing
uncommitted rows into a manifest-vouched segment that `abort_group` can no longer
reach. Not reachable through SQL today (the session layer opens the storage group
inside its commit routine), but `flush`/`compact` are public storage API and state
no precondition. A `debug_assert`/error on `group.is_some()` makes it structural.

### 2.9 — P1 — Commit-log truncation is undetectable

The chain is a pure back-link chain with no length, no head commitment, and no
external anchor, so deleting the last *k* records leaves a valid shorter chain:
recovery resumes from the truncated head and re-issues the deleted `seq`s. The only
defense, `verify_chain_to`, has no production caller and `commit_head` is never
persisted. Boot-path verification is likewise unanchored (genesis-only), and
`\audit` then anchors against the head *that walk produced* — so a wholesale
rewritten log passes recovery and makes `\audit` report `chain_ok = true`.

This is known deferred work (STL-196 / ADR-0026 witness), but the product surface
currently *asserts* integrity it cannot verify post-restart. Worth saying so in the
operator docs before the witness lands. Related: the chain covers commit *metadata*
only (`{txn_id, commit_ts, seq, prev_hash}`), so row data is outside the
tamper-evidence envelope — editing a payload in the redo log leaves the chain
verifying perfectly.

### 2.10 — P1 — `verify_chain_recover` trusts an unverified monotonicity

It takes `commit_ts`/`seq` from whatever record is *last* ("the log is in commit
order"), while correctly tracking `max_txn_id` as a maximum. A chain-valid but
non-monotonic log therefore resumes into `seq`/`commit_ts` reuse, breaking the
global `(sys_from, seq)` total order the bitemporal chain rests on. Accumulate as
maxima, or fail closed on the first non-increasing record.

### 2.11 — P1 — No SIGTERM handler, no graceful shutdown

`signal::ctrl_c()` is the only shutdown arm, so SIGTERM — what every container
runtime and orchestrator sends first — hits the default disposition and terminates
immediately. Even on SIGINT there is no drain: no stop-accepting, no let-in-flight-
finish, no `/readyz` flip ahead of the close. Recovery is exercised on every deploy.
The SIGHUP plumbing already exists (`spawn_tls_sighup_reload`); SIGTERM was missed.

### 2.12 — P2 — `(sys_from, seq)` uniqueness is a precondition nobody enforces

`SysTimeWriter::update`/`stage_update` take `seq` from the caller and never check it
against the version being closed. If `commit == prior.sys_from && seq == prior.seq`,
the close targets the same identity as the new open version, the delta's documented
"idempotent replace" collapses them, and the row is filtered out at *every* snapshot
— silent, permanent data loss with no error. Not reachable in production (the
session engine passes a literal `0` and `MonotonicClock::now()` guarantees distinct
`sys_from`), but it is the load-bearing invariant of the whole model and it is
enforced nowhere in the layer that defines it. Three lines in `stage_update` turn it
into a clean retry.

### 2.13 — P2 — Auto-commit `apply` has no rollback for a partial redo set

The group path buffers redos so `abort_group`→`undo` can reverse a partial apply;
the auto-commit branch appends the WAL record, calls `apply`, and propagates the
error with no `undo` and no poison — leaving the prior version closed with no
successor while the durable record says otherwise. Only a restart reconciles it.

## 3. Correctness

### 3.1 — P1 — `EXPLAIN` bypasses the session time pin and the row cap

`Statement::sql()` returns `None` for `StatementBody::Explain`, so both
`apply_session_time` and `cap_unbounded_select` bail without recursing into
`ExplainStmt::inner`. Under `SET stele.system_time = <past>`, a plain `SELECT` reads
the past but `EXPLAIN ANALYZE SELECT` — which really executes — runs at *now*. That
breaks the equivalence `apply_session_time`'s own doc asserts.

### 3.2 — P1 — `FOR XML`/`FOR JSON`/`FOR BROWSE` and `OUTPUT` are parsed and dropped

`reject_unsupported_query_clauses` never inspects `query.for_clause`, and the
INSERT/UPDATE/DELETE binders never inspect `output` — both of which sqlparser
parses *unconditionally*, not behind a dialect flag. So `SELECT … FOR JSON AUTO`
returns raw rows and `UPDATE … OUTPUT INSERTED.balance` silently discards the
requested rows. The MERGE binder rejects `OUTPUT` correctly, which makes the other
three an oversight rather than policy.

This is the one blind spot in an otherwise disciplined enumerate-and-reject posture:
the reject lists were written against the dialect flags rather than the AST struct
fields. Exhaustive destructuring of `Query`/`Select`/`Insert`/`Update`/`Delete`
would make a sqlparser upgrade that adds a field break the build instead.

### 3.3 — P1 — A NULL bind parameter in a comparison hard-errors

`fold_scalar` returns `FoldError::Null`, which becomes
`UnsupportedPredicate("NULL cannot be compared to column …")`. Defensible for a
hand-typed `WHERE a = NULL`, but the extended protocol substitutes a NULL parameter
as `Value::Null` directly into the AST — so an ordinary parameterized
`SELECT … WHERE balance = $1` with `$1 = NULL` fails where Postgres returns an empty
set. Any driver passing an optional value through a filter hits this.

### 3.4 — P1 — Staged `INSERT` of a live key succeeds, then aborts the transaction

`stage_dml` has a liveness probe for point `UPDATE`/`DELETE` but none for `INSERT`,
and the overlay makes the row visible mid-block. At `COMMIT` the storage layer
rejects with `KeyExists` and the whole transaction is lost. Postgres raises `23505`
on the `INSERT` itself.

### 3.5 — P1 — `repin` is missing on the `EXPLAIN` path under READ COMMITTED

`execute_in_txn_inner` intercepts `Explain` and returns *above* the RC re-pin, so
`EXPLAIN SELECT * FROM t` binds at the `BEGIN`-time snapshot and raises "unknown
table" for a table created since — while the bare `SELECT` succeeds.
`EXPLAIN ANALYZE` additionally captures `txn.snapshot` before the inner re-pins, so
the rendered plan is bound at a different instant than the one that ran.

### 3.6 — P1 — `Describe('P')` on `EXPLAIN ANALYZE <DML>` executes the DML

`returns_rows` treats `Explain` as row-returning, so `handle_describe_portal` falls
through to `ensure_executed`, and under `ANALYZE` the inner statement runs with
auto-commit semantics. A driver that does Bind → Describe and abandons the portal
has still committed the write. The in-code comment claiming "only a row-returning
(read) statement reaches here" is false for this shape.

### 3.7 — P1 — Staged writes carry a `schema_id` that is never validated

`BoundDml` carries the schema version it was bound against, but `apply_bound_dml`
destructures it away and checks only *arity*. Since a re-created table reuses the
tier and namespace, `BEGIN; INSERT INTO t VALUES (1,'x'); DROP TABLE t; CREATE TABLE t
(id INT4, amount INT4); COMMIT;` lands TEXT bytes in an INT4 column — arity
unchanged, identity ignored. One comparison against the live `schema_id` closes it;
`EngineError::SchemaChanged` already exists to carry it.

### 3.8 — P1 — `describe` rejects the introspection surfaces `execute` accepts

`execute_at` recognizes `stele_history(…)`/`stele_segments(…)`/`stele_audit(…)`
structurally; `describe_at` does not, so it calls `bind_select` and returns
`UnknownTable`. Any extended-query client issues `Describe('S')` before `Bind`, so
these work in `psql` and fail in every driver.

### 3.9 — P2 — `valid_as_of` silently prunes on the range paths that claim to ignore it

`execute_range`/`execute_valid_range` document that a `valid_as_of` pin "is ignored",
but both call `prune_segments`, which consults `valid_snapshot` unconditionally at
three sites — while the range resolvers apply no valid-point row filter. The
combination returns only the rows whose segments happen to cover the pin: hard row
loss, not an ignored hint. Not reachable from the engine today, but `SnapshotScan` is
public and the doc invites the combination.

### 3.10 — P2 — RYOW overlay silently absent for a range over a JOIN

`run_select_scoped` routes to `run_join_range` without threading `overlay`, so
inside a transaction a range read over a join returns committed-only rows while the
identical single-table range read overlays. Same statement class, two visibility
rules, no error. An explicit `Unsupported` would be safer than a divergent read.

### 3.11 — P2 — Provenance pseudo-columns accepted in a materialized CTE's `WHERE`

The projection binder guards on `scope.materialized`; `resolve_filter_column` does
not, so `WITH c AS (…) SELECT * FROM c WHERE _stele_txn_id = 5` binds cleanly and
then fails downstream with an internal-looking `ColumnOutOfRange` where a bind-time
`UnknownColumn` belongs.

### 3.12 — P2 — `SUM` returns NULL instead of the answer past `i64`

The `i128` accumulator is right, but the narrowing to INT8 turns a computable sum
into SQL NULL. Postgres promotes `SUM(bigint)` to `numeric`. The differential
oracle cannot catch it — its reference uses `iter().sum()` on `i64`.

### 3.13 — P2 — `hash_join` never checks that the two key vectors share a type

Matching is equality of encoded bytes, so an int4 key can never equal an int8 key:
INNER/SEMI return zero rows, ANTI returns everything, LEFT NULL-extends everything —
silently. The binder does guard this, but STL-327 taught `compare` to promote across
int4/int8/float8, so `hash_join` is now stricter than the `WHERE l.a = r.b` it is
supposed to be equivalent to.

### 3.14 — P2 — Smaller correctness edges

* `Project` cannot address duplicate `ColumnId`s (every exploded value column is
  tagged `Payload`) and silently returns column 0 — or column 0 twice.
* `Predicate::Range` on `BusinessKey` is byte-lexicographic while integer keys
  encode little-endian, so `1` sorts after `256`. Safe today (only `Eq` and
  already-byte-ordered index windows are pushed down); any future integer key-range
  pushdown would drop matching rows.
* A SQL-NULL payload passes every pushed-down payload predicate (`is_none_or`
  yields `true`) — conservative-keep is right for pruning, wrong for a row filter.
* `total_cmp` makes `+0.0 ≠ -0.0`, now reachable since float8 literals fold.
* `parse_uuid` skips hyphens anywhere and any number of times, so
  `'--------550e…'` and `'5-5-0-e-…'` fold to the same key — a silent uniqueness
  surprise. Postgres accepts only bare-32 and canonical forms.
* `1e400` folds to `+inf` instead of raising `22003`; every sibling type in
  `fold_scalar` range-checks, float8 does not.
* `ValidityIndex::active_at`'s doc and code disagree about which candidate is
  filtered (coincide only for a well-formed chain; no production caller pins it).
* `SELECT NULL` and `SELECT 1.5` are rejected — `SELECT NULL` is common driver-probe
  SQL.
* `BEGIN READ ONLY` is accepted and discarded; a read-only transaction can write.
* Unchecked `namespace + 1` in catalog replay, and `next_txn += 1` in five places
  (debug panic / release wrap) where every sibling allocator saturates.

## 4. Performance

### 4.1 — P1 — Any in-transaction read of a written table full-scans and materializes it

`run_select_scoped` routes to `overlaid_rows` whenever the overlay touches the
table, and that path does an **unfiltered** `scan_all_rows`, inserts every base row
into a `BTreeMap`, and collects back to a `Vec` — before filtering. Both the
zone-map/bloom key pushdown and the secondary-index probe are on the *other* branch.
So `BEGIN; INSERT INTO t VALUES (…); SELECT * FROM t WHERE id = 5;` on a 10M-row
table costs a full scan plus two full copies, and the same cost is paid *per staged
point UPDATE/DELETE* (`absent_point_tag` runs a `run_select` probe) — so a block
that stages one INSERT and then a thousand point updates does a thousand full
table scans.

Related: `MERGE`'s cost model assumes per-key probes are bloom-pruned, which is
false under an overlay — so a merge inside a transaction does *probe_keys* full
scans where the "expensive" full-keyset plan would do one.

### 4.2 — P1 — The write path linear-scans and clones the entire resident sealed history

`SealedVersions::versions_for` filters every version of every sealed segment and
clones the matches; `merge::resolve_open` then does a second full pass with another
clone per row. The per-segment bloom (`might_contain_key`) and zone maps exist and
are used by the prune-aware `SealedSegments` sibling — but `Engine::insert/update/
delete` pass `&self.sealed`, so the pruning structures never engage on the hot write
path. Every single-row write is O(total sealed versions).

Compounding: `Delta::candidate_versions` re-reads and re-decodes **every** delta
spill file on every key probe. The validity index solved exactly this with per-spill
range+bloom `SpillMeta` (STL-142); the delta tier has no equivalent. Once the delta
spills (default 64 MiB) the write path is quadratic in a sustained load.

### 4.3 — P1 — Recovery is Θ(tables²) in directory listings

Each tier's recovery performs ~5 full listings of the shared directory, and
`NamespacedDisk::list` filters *after* `inner.list()` has walked and `String`-
allocated every file on the disk. At 10k tables / 50k files that is tens of millions
of allocations and 50k directory walks before the first query. Fix: list once and
hand each tier a pre-partitioned view, or add `Disk::list_prefixed`.

Related: `close_dropped_eras` re-scans every dropped table's full key set on every
boot, forever — boot cost grows monotonically with the accumulated history of every
table ever dropped and never shrinks.

### 4.4 — P2 — `DROP TABLE` is O(live rows) WAL records and fsyncs under the global lock

`close_all_open` loops `delete(key)` with no `begin_group`, so one auto-commit
record + fsync per live key, synchronously, while the single engine mutex is held.
Dropping a million-row table stalls every connection for a million fsyncs. Wrapping
the closes in a group commit makes it one record.

### 4.5 — P2 — One syscall and three allocations per result row

`write_data_row` per row with no `BufWriter`: a fresh `BytesMut` with no capacity
hint, a `String` per cell, then a second `BytesMut` in `write_framed`, then
`write_all`. On plaintext that is one `write(2)` per row; over TLS, one **TLS record
per row** (~29 B framing + a fresh AEAD seal each). A 1M-row result is 1M syscalls
and ~3M allocations. Batching into a shared buffer flushed every N KiB is a large,
low-risk win.

### 4.6 — P2 — The extended protocol ignores `Execute`'s `max_rows` server-side

`execute_stmt` runs to completion and buffers every row into the portal before a
single `DataRow` is written; `max_rows` only slices the buffer. The row cap is
applied on the simple path only, with a comment justifying the exemption because
"the driver drives row count through `max_rows`" — true of the client, false of the
server. `Parse`+`Bind`+`Execute(max_rows=1)` still materializes the whole table.

### 4.7 — P2 — The one big engine lock serializes every connection

`Arc<Mutex<dyn SessionHandle>>`, one per server, held for the full duration of every
dispatch — scan, filter, sort, projection, WAL append and fsync — and `BACKUP` holds
it across a full flush + checkpoint + byte copy. This is a deliberate trade (it is
what makes the conflict-check/apply TOCTOU impossible and lease registration
race-free), but it caps throughput at one core and should be recorded as a known
ceiling rather than discovered under load. The per-table tier lock is the natural
next split.

### 4.8 — P2 — Per-row allocation throughout the executor inner loops

The zero-copy `Cells`/selection-vector machinery is good at the batch boundary, but
every inner loop still allocates per row: `Expr::Column` deep-clones the whole
decoded column per reference (`a > 1 AND a < 10` clones `a` twice per batch);
literal broadcast materializes a full-height vector (`vec![Some(s.clone()); rows]`);
`Vector::get` clones Text/Bytea and is the inner loop of aggregate, join, and
distinct; sealed business keys are cloned ~5× per candidate row; `build_column`
deep-copies every cell out of the resolved versions, so the scan's own output is a
full row-major copy. Hash join uses a `BTreeMap<Vec<u8>, …>` (one allocation per
build *and* probe row, O(log n) byte-slice compares) with no `reserve`.

### 4.9 — P2 — Other hot-path costs

* WAL replay opens the segment file up to 3× *per record* (`segment_len` per record,
  plus two `read_segment` calls), making a cold recovery syscall-bound.
* `SegmentWriter::finish` still copies each chunk to compute its CRC (the reader
  side was converted in this pass; the writer was not).
* `flush`/`compact` clone every `Version` into the writer while retaining the
  source, so compaction peaks at 2–3× the full history.
* Group/bulk commit clones every redo before applying it, so a bulk `COPY` holds two
  copies of every row.
* `row_group_zone_maps()` rebuilds and re-allocates every row-group's map on every
  call (the segment-level map is cached at open; the per-row-group ones are not),
  and `zone_map_from_metas` is O(columns² × chunks).
* `ScanSource` is eager — `LIMIT 1` materializes every live row of every surviving
  segment.
* The range path reads every delta spill before filtering, where the point path
  filters during the read.
* `TxnManager::write_index` grows without bound (every key ever committed, never
  removed).
* The CLI runs PBKDF2 twice per authentication (`client_proof` then
  `ScramVerifier::derive`, each a full 4096-round `hi`).

## 5. Testing gaps

* **Every crash test crashes exactly once.** The three P0 durability findings (2.1,
  2.2, 2.8) all live in state transitions the tests never compose:
  recover-then-write-then-recover, commit-without-checkpoint-then-corrupt, and
  flush-while-a-group-is-open.
* **The crash model cannot lose unsynced bytes.** `MemDisk` writes appends straight
  through and `sync` is a pure fault hook, so no seed can model "the process died
  with staged-but-unsynced bytes the OS never wrote" — the canonical crash, and
  exactly what `durable_fence` exists to gate. Every torn-tail test instead
  hand-truncates the file out of band, which a real `Disk` cannot do.
* **`FaultDisk` has no lost-write, non-atomic-rename, or missing-directory-fsync
  fault**, though the taxonomy comment claims to cover the classes "a real disk
  exhibits under power loss".
* **The catalog log's two real failure modes are untested** — the existing test uses
  a clean `FaultOp::Append` and never `FaultOp::Sync` (see 2.3).
* **The conformance suite doesn't pin the one semantic where the backends differ**:
  `MemFile::len` reads the shared buffer live, `LocalFile::len` returns a per-handle
  counter frozen at open — and `Wal::append`'s torn-detection keys off `len()`.
* **No direct round-trip test** for `SegmentWriter` → footer → `might_contain_valid`;
  coverage is end-to-end only, and the row-group↔summary index alignment is the part
  most likely to break under a refactor.
* **Group/`DISTINCT` output order** is little-endian byte order, documented as such,
  but every test uses small positive integers where LE agrees with value order.

## 6. Structure & documentation

### 6.1 — `stele-engine/src/lib.rs` is 22,839 lines

One `impl SessionEngine` spans ~7,000 lines with 457 methods; ~12,000 lines are a
single inline `mod tests`. Per-item rustdoc is uniformly good (and now enforced) —
the problem is purely navigational. Cheapest first step: move the tests to
`crates/stele-engine/tests/` (several already live there), which halves the file.
Then split along seams the code already has: `clock`, `disk`, `error`, `txn`
(+`txn/conflict`), `commit/group`, `ddl`, `recovery`, `admin`, `read/{select,range,
join,overlay}`, `write/dml`, `introspect`. `stele-sql/src/select.rs` (10.5K) wants
the same treatment.

### 6.2 — Crate-wide `#![allow(dead_code)]`

Present in `stele-storage`, `stele-catalog`, and `stele-sql` — justified as
"scaffold" in crates that are now substantially complete. With `missing_docs` now
enforced and clippy pedantic+nursery under `-D warnings`, these blanket allows are
the only remaining holes in the wall, and they hide exactly the drift documented in
6.3. Narrow them to the specific items still forward-looking.

### 6.3 — Docs that contradict the code

Each of these is the kind a reviewer trusts instead of re-deriving:

* `docs/02-architecture.md` §3.7 — "a complete frame whose CRC fails … fails closed"
  holds only under the checkpoint fence (2.2). §3.7 and `docs/segment-format.md`
  also say segments are checksummed "per page"; the unit is the per-column *chunk* —
  there is no page concept in the format.
* `EngineError::CatalogLog` — "the DDL is refused — nothing was acknowledged" is
  false for a torn append and for append-then-failed-fsync (2.3).
* `commit_poisoned`'s doc reads as a whole-session stop; before this pass only
  `execute` was guarded (now fixed).
* `SessionEngine::commit`'s `# Errors` says a partially-applied commit is "not yet
  rolled back in memory"; single-table legs *are* rolled back — only the cross-table
  case (2.5) is not. Mirrored stale in `stele-pgwire`.
* `stele-pgwire`'s crate docs still say "no auth in v0.1" and list COPY and
  SCRAM-SHA-256 under "Not yet" — both landed. A reader of the module header gets
  the wrong security posture.
* `delta/version.rs` — "the per-key chain does not yet *order* on `(sys_from, seq)`"
  — it does, and that is the layer's most load-bearing invariant.
* `stele-txn/manager.rs` — "recovering [the conflict index] on restart arrives in
  v0.2" and "a v0.1 transaction is single-statement"; both landed.
* `stele-catalog/lib.rs` — "Scaffold only at v0.1", contradicted by the same file
  30 lines later.
* `rebuild.rs` — "the WAL is truncated once its records are durably folded into
  segments" vs `backend/mod.rs` "the WAL does not delete its segments, by design".
  No truncation exists; the floor advances instead.
* `Engine::recover`/`recover_replay` still describe pre-STL-177 full-WAL replay,
  contradicting a correct comment four lines above.
* `Engine::flush`'s doc names a `segment_count` manifest field that ADR-0030
  replaced with an explicit live-segment list.
* `reader.rs` — the claim that in-loop growth "is bounded by the file's actual size"
  was true only for `Codec::Plain` (fixed in this pass).
* `read_footer` — cites the u32 width as the allocation bound; a u32 permits 4 GiB.
  The real (adequate) bound is the `checked_sub` above it.
* `ScanStats`' partition formula omits `segments_pruned_valid`, and "three
  complementary prunes" is now four.
* `Vector::Float8` — "the evaluator neither compares nor computes over it"; compare
  has promoted float8 since STL-327.
* `select.rs` — "the join path rejects HAVING"; `bind_join_aggregate` binds it.
* `docs/sql-grammar.md` — "`<expr>` is any scalar expression" for `AS OF`; the
  resolver accepts only `now()`, `now() ± interval`, a bare integer, or parens
  around those. The same file states it correctly 500 lines later.
* `README.md` lists "lineage & provenance" among shipped differentiators
  (`stele-lineage` is 14 lines of doc comment and `#![allow(dead_code)]`) and lists
  "encryption + KMS/BYOK, RBAC/RLS/CLS, crypto-shredding erasure" under **Security**
  with no "planned" marker — none of which exist.
* `docs/05-dev-environment.md` describes `--dev` as supplying "safe defaults" (1.2).

### 6.4 — Undocumented semantics a client author needs

That a staged point `UPDATE`/`DELETE` matching zero rows is deliberately kept out of
the write set *and* out of conflict detection; that `INSERT` uniqueness is deferred
to `COMMIT` (3.4); that the write buffer is unbounded (1.9); that DDL inside a block
survives `ROLLBACK`/`ROLLBACK TO` (the savepoint API is where a user will look); and
that under READ COMMITTED a buffered write is applied at `COMMIT`, not at statement
time — so the read-then-write window spans the whole block.

### 6.5 — Panic surface in public APIs

Under `panic = "abort"` each is a process kill. None is reachable from today's SQL,
but several are one plan change away: `DdlStatement::apply`'s `unreachable!()` on
the three user-DDL variants (public API); `hash_key`/`scalar_cmp` on float8;
`execute_range`/`execute_valid_range`'s `expect` on a missing range (public methods);
`GatheredColumns::bytes`; `Vector::get`/`gather`; `Column::take`;
`SegmentReader::read_column_in_row_groups` indexing a caller-supplied set; and the
seven `unreachable!()`s in engine DML/overlay code guarding the same internal
contract that `apply_bound_dml` chose to *error* on. The crate's own precedent argues
for errors.

## 7. Fixed in this pass

For the record, so these aren't re-reported:

| Finding | Fix |
|---|---|
| Dictionary-decode amplification: a ~32 MB crafted segment could name ~256 TiB on the recovery path | Per-entry cap at `MAX_VERSION_FRAME_LEN` (the write-path invariant) + running total cap; both fail closed as `TooLarge` |
| Lost update: `repin_snapshot` advanced the write-write conflict anchor, so a DDL-in-txn or any READ COMMITTED statement silently forgave a conflict | Per-write `write_anchors` parallel to `writes`; `commit` tests each write against its own staging snapshot. Regression test covers both re-pin routes |
| Commit-log poison guarded only `execute` — `stage_dml`, `commit`, COPY, and the typed insert/update/delete all bypassed it | Extracted `refuse_if_commit_poisoned` and applied at all seven entry points |
| Unbounded `EXPLAIN` recursion → stack overflow → process abort (sqlparser's depth guard does not apply; each level builds a fresh `Parser`) | Nested `EXPLAIN` refused from the token stream *before* recursing; depth bounded at 1 |
| Θ(qualifiers × tokens) token cloning from repeated `FOR … AS OF` → worker stall | `MAX_AS_OF_QUALIFIERS` cap; the binder rejected >1 per axis anyway |
| CRC32C was byte-at-a-time on every persisted byte | Slice-by-8 kernel + incremental `Crc32c`; **0.39 → 1.82 GiB/s (4.7×)**, byte-compatibility pinned by a differential test against the old kernel |
| Segment chunk read copied the payload 3× (CRC buffer, then `to_vec`) | Incremental CRC over the two discontiguous pieces + `drain` — one copy |
| 29 undocumented public items; `missing_docs` was `allow` | All documented; lint flipped to `warn`, so CI's `-D warnings` now makes an undocumented addition a red build |
